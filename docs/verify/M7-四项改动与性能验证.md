## 一、导入课表支持「覆盖原课表 / 插入原课表」

### 做了什么

| 层 | 改动 |
|---|---|
| 领域 | 新增 `domain/model/ImportMode.kt`（`REPLACE` / `APPEND`） |
| 仓库 | `applyImport(schedule, mode)`；契约与实现同步 |
| 导入通道 | `ScheduleImporter.commit(parsed, mode)` + 3 个实现（WakeUp CSV / 教务 / 文件） |
| 视图模型 | `ImportPreviewUiState.mode` + `setMode()`；覆盖范围的统计口径改为**跨来源求和** |
| 界面 | 预览页新增 M3 单选分段按钮「覆盖原课表 / 插入原课表」，说明与覆盖范围文案随选择联动 |

### 两种模式的确切语义

- **覆盖原课表（默认）**：清空当前学期**全部非手动来源**的课程，再写入本次内容。
  → 课表 = 本次导入的内容 + 手动添加的课程
- **插入原课表**：不清任何东西，本次课程追加进现有课表。
  → 课表 = 原有内容 + 本次导入的内容

两种模式下**手动添加（MANUAL）的课程都永不删除**（AC-20 双防线不随 mode 改变）。

### 注意 一处语义修订（需要你知道）

原来的实现是「**按来源**整体替换」——导入教务来源时只清教务来源，导入文件来源时只清文件来源。

**这次改成了「清空全部非手动来源」**，理由是真机上的实测数据：你手机里同时有

```
WEB（教务）      9 门
FILE_JSON（文件） 9 门   ← 与 WEB 的 9 门同名同老师、内容完全相同
MANUAL          1 门
```

按旧语义选「覆盖」，只会清掉 FILE_JSON 那 9 门，WEB 的 9 门原封不动 → **重复依旧**。
按「覆盖原课表」的字面含义，用户期待的是"课表变成这份内容"，所以改成清全部导入来源。

**这确实推翻了 M2 时期的一条既有裁决**（见 `ImportSourceScopeTest` 原文件头注释：
"若实现成整学期清空 → 静默删除用户课程（不可逆），故按来源整体替换"）。
之所以认为可以改：当年担心的是"**静默**删除"，而现在——① 清空规模会在预览页明示
（"将清空本学期现有导入课程 N 门"）；② 是用户**主动选择**「覆盖原课表」的结果；
③ MANUAL 双防线依旧不动。若你更想要"只清同来源"的保守行为，告诉我，改回来是一个分支的事。

### 测试

并**新增 2 个插入模式用例**。单测总数 243 → **245**，全绿。

## 三、滑动流畅度优化

### 最终采用的方案（3 项，全部是"减少工作量"）

| # | 改动 | 位置 |
|---|---|---|
| 1 | `beyondViewportPageCount` 由 **0 → 1**（前后各预组合一页） | `WeekPager.kt` |
| 2 | 课程点击回调用 `remember` 稳定化（原本是 page lambda 内的内联 lambda） | `WeekPager.kt` |
| 3 | 计算按输入缓存：按天分组、作息按节次建索引、周次守卫判定 | `WeekGrid.kt` |

### 实测数据（真机，横向翻周 20 次，预热后）

| 指标 | 优化后（=1） | 对照（=0，仅此一项不同） | 变化 |
|---|---|---|---|
| **卡顿帧** | **2 帧（0.09%）** | 9 帧（0.45%） | **降低 5 倍** |
| **90th percentile** | **13 ms** | 20 ms | −35% |
| **95th percentile** | **20 ms** | 42 ms | **−52%** |
| Slow UI thread | 2 | 9 | — |

> 90th = 13ms **已进入 60fps 的 16.7ms 预算内**；项目判据「卡顿率 < 5%」大幅达标。
> 对照只隔离了第 1 项（其余两项在两版中都生效），所以这是 `beyondViewportPageCount` 的**单变量**贡献。

### 为什么是这三项（以及**为什么没做**你提到的另外两条）

**第 1 项是主因**。原值 0 意味着滑动时邻页**不参与组合**，翻周瞬间要现场组合整页
（表头 + 网格 + 全部课程卡片）——这正是 `Number Slow UI thread` 占全部卡顿的原因。
改成 1 后邻页提前组合好，翻周时直接复用。代价是内存多保留 2 页的组合结果，
而本项目单页元素量很小（7×12 格 + 十几张卡片），**内存换流畅是划算的**——这正对应你说的"适当增加缓存"。

**关于"提高 CPU 优先级 / 增加功耗预算"（ADPF 那类手段）——本次未采用**，理由：
- 实测显示卡顿**全部**来自 `Slow UI thread`（44/44 帧），即"一帧内要做的事太多"，是**工作量问题**，不是 CPU 调度问题；
- ADPF（`PerformanceHintManager`）的设计目标是让**长时任务**（游戏渲染、视频编码）获得持续的性能保障，
  对"偶发几十毫秒的组合尖峰"帮助有限；
- 引入它会增加一套需要随生命周期管理的会话对象，而收益无法用数据证明——按项目一贯纪律，
  **不给没有实测支撑的优化加代码**。若后续出现"持续高负载"场景，再评估不迟。

**关于换 `LazyColumn`**——实测发现**没有意义**：课程表内容高度（12 节 × 52dp ≈ 624dp）
**小于屏幕可用高度**（853dp），横向翻周之外的纵向"滚动"根本不会发生
（测量纵向滑动时 `Total frames rendered: 0`，即一帧都没渲染）。改了不会有任何收益。

## 四、小组件刷新逻辑

### 做了什么

1. **回到前台即刷新**：`MainActivity.onResume()` → `WidgetRefresher.refreshOnForeground()`，
   带 30 秒节流（避免 App 频繁前后台切换造成无谓重绘）。
2. **系统周期兜底**：`today_widget_info.xml` 的 `updatePeriodMillis` 由 `0` 改为 `1800000`（30 分钟，系统允许的最小值）。

### 注意 必须说清楚的技术限制

**Android 的小组件没有"变为可见"的回调**——Glance 和传统 RemoteViews 都没有，
系统也无从告知 App"用户正在看桌面"。所以"小组件出现时立即刷新"在平台层面**做不到**。

原先是"点进 App 才刷新"的根因是：刷新全部由**进程内事件**驱动（App 启动 / 数据变更），
用户长时间不进 App 时，只能靠点进去触发一次进程启动来顺带刷新。

本次补的两条是**最接近该效果的可控时机**：
- 第 1 条覆盖"用户与 App 有过交互后看桌面"；
- 第 2 条覆盖"长时间不开 App"（由系统调度，不依赖我们自己的闹钟逻辑是否失效）。

配合既有的跨天闹钟（每日 00:05）与课后闹钟，共四条链路保证"该看到新数据时就是新的"。

**第 2 条的代价（已写进 XML 注释）**：设备**醒着**时每 30 分钟触发一次重绘
（读本地库 + 重绘一个小组件，毫秒级）；平台保证该机制**不唤醒休眠设备**，对续航影响很小。
但这确实改变了原先"完全不用系统周期刷新"的省电取向——**如果你更看重省电，把该值改回 0 即可**，
第 1 条（回前台刷新）会独立生效。

# 追加：第二轮优化（同日 18:30+，针对"课程多时卡 / 刚打开卡"）

## 一、每节课结束刷新小组件 —— 修掉一个真实缺陷

`TodayWidget.nextEndEpochMilli` 原为 `plan.remaining.firstOrNull()?.endMinute`。
但 `remaining` 按**开始时间**升序 —— 取第一项等于取"开课最早"的课，**未必最早结束**。
例如同日「A 课 1–4 节」+「B 课 2–3 节」时，B 先结束，原实现把闹钟挂在 A 的结束时刻，
**B 结束时小组件不会刷新**。

改为 `plan.remaining.minOfOrNull { it.endMinute }`（取最早结束时刻）→ 真正"每节课结束都刷"。

> 另外确认：4002 的**恢复链路完整**（BOOT / 时间变更 / 时区变更 / 精确闹钟授权变化 /
> 覆盖安装都会 `WidgetRefresher.refreshAll` → `provideGlance` → 重排 4002）。
> 真机上 4002 当时不在册是因为**今天（周三）的课已全部结束**，`remaining` 为空 → 按设计取消。

## 二、卡片渲染优化（"卡片越多越卡"的根因）

`CourseCard` 每张持有：

- 2 个 `animateFloatAsState`（按压缩放 + 透明度）
- 1 个 `MutableInteractionSource` + 1 个 `collectIsPressedAsState` 订阅

卡片是全项目数量最多的可组合单元（一天 4–5 节 × 横向预组合 3 页 = 数十张），
于是变成**几十个常驻动画状态**，每次重组逐个检查 —— 这就是"卡片越多越卡"。

移除后（点击能力保留，无涟漪），另有两处稳定性/缓存修复：

- `ConflictGroup` 传 `onCourseClick` 稳定引用，不再构造 `{ onCourseClick(item) }` 内联 lambda
  （原先每卡片每次重组都新建 lambda，使 `CourseCard` 无法跳过重组）；
- `ConflictGroup` 的 `min/max/groupHeight/CellLayout.arrange` 按 `(group, cellWidth)` 缓存；
- 时间轴文字样式按 `Typography` 缓存（原为每节每个 Text 各 `copy()` 一次，
  12 节 × 2 × 预组合 3 页 = 每帧 72 个新 TextStyle）；
- 7 天的 `BoxWithConstraints`（= 7 个 `SubcomposeLayout`）合并为外层 1 个。

## 三、⭐ 关键发现：一直在用 **debug 版**（这才是"刚打开卡"的主因）

APK 一直是 `assembleDebug` 产物。debug 版无 R8 优化、`debuggable=true` 会抑制 ART 优化。
构建 **release 版**（用 debug 密钥签名以便覆盖安装、保留数据）后实测：

| 场景 | debug 基线 | debug + 卡片优化 | **release + 优化** |
|---|---|---|---|
| 冷启动 `TotalTime` | 642–710 ms | 642 ms | **284 ms（−58%）** |
| 冷启动 90th | 550 ms | 500 ms | **129 ms（−77%）** |
| 冷启动 95th | 600 ms | 550 ms | **129 ms（−79%）** |
| 翻周卡顿率 | 0.49% | 0.14% | **0.04%（↓12 倍）** |
| 翻周 90th / 95th | 18 / 29 ms | 16 / 22 ms | **9 / 12 ms** |

- 体积：debug 21.3 MB → release **7.6 MB**
- 90th 9 ms **远低于** 60fps 的 16.7 ms 预算
- 数据完整保留（覆盖安装同签名）

> **代价（必须知道）**：release 版 `debuggable=false` → `adb run-as` 不可用（读不了库）、
> App 自身日志等级受限。用于日常使用没问题，但**我后续做需要读库的验收时要临时换回 debug 版**。
> 另外它用的是 **debug 密钥**签名 —— 仅为此处验证性能；**将来发布 GitHub Releases 前需要换正式
> release keystore**（并注意换签名会导致无法覆盖安装，需卸载重装、数据会丢）。

## 二、小组件周期刷新：30 分钟 → **每小时**

按产品负责人选择，`updatePeriodMillis` 由 `1800000` 改为 `3600000`（每小时）。
