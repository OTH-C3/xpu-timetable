## 五、🔵 P3：我的规格 §8 的 grep 检查有缺陷（非实现问题）

### 现象

实现方回传里主动说明了唯一一处偏离：

> §3.3 照抄代码的注释里含字面量 `NavigationBarItem`，会让 §8 第 2 条 grep 返回 1（期望 0）。
> 已把两处注释改为「NavigationBar 的条目项」表述。

实测确认（`AppBottomBar.kt`）：

```
第 6 行：  * M6-fix ①：去掉图标，只保留文字 → NavigationBar 的条目项 icon 为必填且布局固定为
第 109 行：                selected = isSelected     // 无障碍：暴露选中态（替代原 M3 底栏条目项的语义）
```

### 裁决：这是**我的规格缺陷**，不是实现的缺陷

我 §8 写的自证命令是：

```bash
grep -c "NavigationBarItem" .../AppBottomBar.kt      # 期望 0
```

**它没有排除注释**。而我在 §3.3 给的照抄代码里，注释**本来就要写 `NavigationBarItem`**
（解释「为什么不能用它」）。两条要求**自相矛盾**。

**实现方的处理是合理的**：它发现矛盾后，选了「改注释」而非「改规格」——因为它只能改代码，且**主动说明了偏离**。这比默默改掉要专业。

### 但代价是：注释里精确 API 名丢失

- 未来的维护者搜 `NavigationBarItem` 时，**找不到这条「为什么不用它」的记录**
- 「NavigationBar 的条目项」措辞含糊（读者不确定指哪个具体组件）

### 建议修法（一行，可选）

把 grep 改成**带左括号**，即可排除注释：

```bash
grep -n "NavigationBarItem(" .../AppBottomBar.kt      # 期望 空
```

然后注释可恢复精确措辞（`NavigationBarItem 的 icon 为必填`）。

**定级 P3**：不影响功能、不影响门禁、不影响契约，仅影响注释可搜索性。

### 沉淀的纪律（已写入 skill）

> **用 grep 做自证时，pattern 必须能排除注释**。否则「注释里解释为什么不用 X」与「grep 断言没有 X」
> 会自相矛盾，逼着实现方写含糊的注释。
> 具体做法：匹配 API 名时带上调用符号（`Foo(`、`Foo::`），或在 grep 前用 `sed` 剥掉注释行。
