## 四、🔴 重大发现：88dp 在真机上物理不可达（规格级问题，需裁决）

### 4.1 实测证据

| 步骤 | 结果 |
|---|---|
| 长按小组件 → 尺寸调节 → **拖底部手柄到最小** | 高度仍 **631px = 168.3dp**（2 格网格） |
| 设备密度 | 1440×3200 @ 600dpi → **1dp = 3.75px** |
| 推算 **1 格高度** | 631px ÷ 2 = **84.1dp** |
| `minResizeHeight` | 88dp **>** 84.1dp |

**结论**：launcher 按网格取整，88dp 落在 84.1dp（1 格）与 168.3dp（2 格）之间，
最接近的合法尺寸是 2 格。**88dp 在本机既非 1 格也非 2 格，物理上无法达到**。
这不是 App 缺陷，是设备网格密度决定的。

### 4.2 几何推演（基于实测部件高度）

```
完整布局（列表 + 交替底色 + 统计行）最小高度需求：
  头部        19.5 dp
  间隔 Spacer  6.1 dp
  首个课程行   39.7 dp
  统计行      14.7 dp
  ─────────────────
  固定内容    80.0 dp
  + 上下 padding 24.0 dp
  = ★ 最小需要 104.0 dp
```

| 目标高度 | 余量 | 判定 |
|---|---|---|
| 110 dp | +6.0 dp | ✅ 放得下 |
| 100 dp | −4.0 dp | ❌ 底部统计行被裁 |
| **88 dp** | **−16.0 dp** | ❌ **底部统计行被裁** |

紧凑布局（`CompactContent`：单行 + 统计行）估算：
```
头部 19.5 + 间隔 6.1 + 紧凑行 ~28 + Spacer 2 + 统计行 14.7 + padding 24 ≈ 94.3 dp
→ 目标 88dp 余量 −6.3 dp ❌ 仍溢出
```

### 4.3 规格假设失效

规格 §5.1 原文：「把 `COMPACT_HEIGHT` 改为 **80.dp**（这样 88dp 仍走完整布局：
列表 + 交替底色 + 统计行）」。

**实测证伪**：完整布局最少需 **104dp**，88dp 下必然裁掉底部统计行；
连紧凑态（94.3dp）也放不下。规格对 88dp 的容量假设偏高约 16dp。

同时，规格 §5.1 担忧的「88dp 放不下 4 行 → MAX_ITEMS 降为 3」在本机 **168dp 实测下不成立**
（168dp 只有 1 节课，未触及上限）；真实瓶颈是 **88dp 连 1 行完整布局都放不下**。

### 4.4 待产品裁决（三选一）

| 方案 | 内容 | 代价 |
|---|---|---|
| **A. 接受现状** | 88dp 仅作 `minResizeHeight` 声明，实际尺寸由网格决定；统计行被裁属预期 | 默认放置（2 格=168dp）观感正常；仅用户在极密网格设备上缩到 88dp 时统计行被裁 |
| **B. 回退到 110dp** | `minHeight=110dp / minResizeHeight=110dp`（回到 M4-W 值） | 完整布局有余量 +6dp，任何可达尺寸都不裁；但放弃「缩 1/5」需求 |
| **C. 88dp 显式降级** | 88dp 下走紧凑态并**保留统计行**（去掉教室行、缩短色条） | 需新增降级分支与文案，且 94.3dp > 88dp 仍差 6.3dp，须再压缩 padding |

> **建议**：选 **A** 或 **B**。C 需要重新设计尺寸令牌且仍差 6.3dp，投入产出比低。
> 若老大认为「缩 1/5」是硬需求，则选 A（声明值保留，实际由网格决定）。
