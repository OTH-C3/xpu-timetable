# ADR-005: 使用 OkHttp + kotlinx.serialization 处理网络与解析，不引入 Retrofit / Ktor

- **Status**: Accepted (2026-09-16)
- **Date**: 2026-09-16
- **Deciders**: 项目维护者
- **Related ADRs**: ADR-006（WebView 捕获策略，网络层的实际使用场景）、ADR-003（Room 存储解析结果）

## Background

本项目的网络需求极其特殊，必须先说清事实：

- App 不访问任何自建后端，也不做"多端点 REST 调用"。
- **唯一的网络交互发生在 WebView 内部**：用户在 WebView 中登录学校一网通办并加载课表页，页面自身的 XHR/fetch 由系统 WebView 发起。
- OkHttp 的实际职责是导入主通道的辅助角色：在 `shouldInterceptRequest` 命中特征请求时**代发请求并把响应体分流**（一份回给 WebView 正常渲染，一份交给解析器）；此外用于站点可达性探测。
- 需要 JSON 解码，但**接口路径与字段结构在首次真机抓包前是未知的**（Phase 0 OPEN 项 #2）。

候选方案：

1. OkHttp 5.4.0 + kotlinx-serialization-json 1.11.0（裸客户端 + 手写 DTO）；
2. Retrofit + kotlinx-serialization converter（声明式接口）；
3. Ktor Client（Kotlin 原生多平台客户端）。

## Decision

**采用 OkHttp 5.4.0 + kotlinx-serialization-json 1.11.0。**

配套规则（必须遵守）：

1. JSON DTO 全部为 `@Serializable data class`，集中放在 `parser/xpu/dto/`，与领域模型分离（防腐层，见架构文档 §5.3）。
2. 所有 `Json` 实例必须开启 `ignoreUnknownKeys = true`——教务接口字段未知且随时可能增加，未知字段容忍是硬要求，缺此配置会导致上线后一次接口加字段即崩溃。
3. 需要同时应用 Gradle 插件 `org.jetbrains.kotlin.plugin.serialization`，版本随 Kotlin（2.3.21）；运行时库与插件版本必须成对（1.11.0 基于 Kotlin 2.3.20 编译）。
4. 超时显式配置（连接/读取超时各 15 秒），禁止依赖默认值无限等待。
5. 无重试风暴：导入路径的重试由用户在 UI 上显式触发，禁止自动轮询。

## Consequences

### 正面

- 抽象层级与需求匹配：只需"发一个请求、拿到一段字符串、自己解码"，三层代码即可完成，不存在被浪费的抽象。
- 体积与依赖最省：OkHttp + Okio + serialization 运行时合计约 1.1–1.5 MB；Retrofit 与 Ktor 都会额外引入一层依赖树。
- 与未知接口共存的灵活性最高：接口路径未知时，手写 DTO + 特征匹配的拦截器比 Retrofit 的接口声明（需要先知道路径与方法）更适配探索期。
- 与 WebView 拦截场景天然贴合：`shouldInterceptRequest` 里做的就是"代发并拿到原始响应体"，OkHttp 的同步/异步调用模型直接可用。

### 负面 / 代价

- 无声明式接口代码生成，DTO 需要手写并保持与教务字段同步（缓解：字段映射收敛在 `parser/xpu` 一个包，改版只改这里）。
- 无内置的调用适配与错误分类，错误处理需自行实现——本项目已按 `ImportError`/`ParseError` 结构化枚举要求实现（架构文档 §8.2），不依赖框架。
- 响应体分流（tee）需要手动把 `ResponseBody` 读成字节数组再构造 `WebResourceResponse`，注意在 IO 线程执行并控制内存占用（课表 JSON 体量小，无实际风险）。

### 已否决选项的代价说明

- **Retrofit**：其价值在于"多端点 + 声明式接口 + 转换器生态"。本项目端点未知、数量为 1、且主要数据通路走 WebView，Retrofit 的接口层在此为负资产（先要知道 path 才能声明，探索期反而阻碍）。
- **Ktor Client**：功能完备且跨平台，但本项目无多平台需求，其 engine/plugin 体系的依赖与配置成本高于收益。
