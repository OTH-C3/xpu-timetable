# ADR-008: 使用 Navigation 3 作为导航框架

- **Status**: Accepted (2026-09-16)
- **Date**: 2026-09-16
- **Deciders**: 项目维护者
- **Related ADRs**: ADR-001（Compose）、ADR-007（单模块结构）

## Background

App 有 4 个页面：周视图（主页）、导入中心、课程编辑、设置；另有导入主通道的 WebView 捕获页（可作为独立目的地或独立 Activity/全屏层）。导航需求简单：栈式前进/返回，无深链接、无多窗格、无复杂参数传递（最多带一个 courseId 或 termId）。

候选：

1. **Navigation 3**（`androidx.navigation3`，1.0.0 于 2025-11-19 stable，1.1 系持续修复）；
2. **Navigation Compose 2.x（Nav2）**（`androidx.navigation:navigation-compose`，2.10.0 于 2026-08 stable，生态最成熟）；
3. **手写导航**（一个 `when` 状态 + `BackHandler`，零依赖）。

约束：页面数少但需要正确的返回栈与状态保存行为（返回时必须保留周视图的周次滚动位置等）；项目维护者为新手，教学可解释性重要；官方已明确 Nav3 是新 Compose-only 应用的推荐方向（稳定版公告明确说明"可用于生产"，并提供从 Nav2 的迁移指南与 recipes 仓库）。

## Decision

**采用 Navigation 3（`androidx.navigation3` 1.1.x）** 作为导航方案，配合 `NavKey` 类型化目的地与 `NavDisplay`。

落地规则：

1. 目的地以类型化 `NavKey` 定义（`ui/navigation/NavKeys.kt`），禁止字符串路由模板；
2. 返回栈状态由项目自定义的持有类管理（`rememberNavBackStack`），不引入第二套导航状态源；
3. WebView 捕获页作为独立目的地入栈，返回时取消导入流程必须清理会话（不得依赖 Activity 销毁做兜底）。

## Consequences

### 正面

- **心智模型更简单，对新手更友好**：返回栈就是一个由 `SnapshotStateList<NavKey>` 持有的列表，`NavDisplay` 观察它渲染——没有 Nav2 的 NavController / NavGraph / route 模板 / 图内嵌图三层概念，也没有"导航状态有两份（框架内 + 自己的 UI 状态）"的经典困惑。
- 官方新应用推荐方向，Compose 原生，页面动画与多窗格能力预留（未来平板适配不需要换框架）。
- 与 Compose 状态驱动完全一致：本项目的状态管理（ViewModel + Flow）可与导航状态自然组合。
- 页面数少是本项目采用新库的低风险区：迁移面小、可回退。

### 负面 / 代价

- 社区存量教程与问答远少于 Nav2（Nav2 有近 7 年积累）。新手检索时需辨别适用版本（缓解：本项目文档作为第一参考源；官方 recipes 仓库覆盖常见场景）。
- 1.1.x 仍在活跃修补（1.1.7 为当日最近版本【核对】），需在首次构建时确认具体 patch 版本可用。
- 生态周边（部分第三方库的 Nav2 集成）不适用；本项目无此类集成需求。
- 若未来出现"必须用某 Nav2-only 组件"的硬需求，回退成本为中等（导航代码面小，且 Nav3 提供官方迁移指南的反向参考）。

### 已否决选项的代价说明

- **Nav2（Navigation Compose 2.x）**：最成熟的保守选择，但引入的是被官方标注为"为新应用考虑迁移"的上一代模型，且概念层数更多。对 4 页面的简单应用，Nav3 的学习成本实际低于 Nav2，这是本次与"选最保守选项"直觉相反的判断依据。
- **手写导航**：零依赖且完全可控，但需要自行处理返回栈、状态保存、返回手势与预测性返回的正确配合——被官方组件已经解决的细节重新手写，风险高于依赖收益；且未来扩展（如深链接）需要重写。
