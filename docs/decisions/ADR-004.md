# ADR-004: 使用手动 DI（AppContainer），不引入 Hilt / Koin

- **Status**: Accepted (2026-09-16)
- **Date**: 2026-09-16
- **Deciders**: 项目维护者
- **Related ADRs**: ADR-007（单模块结构）、ADR-003（本地存储，被装配对象）

## Background

App 需要在各层之间传递依赖：数据库、DataStore、OkHttp 客户端、若干仓库实现、各页面 ViewModel。可选方案：

1. **手动 DI**（Application 层持有一个 `AppContainer`，用普通 Kotlin 构造函数装配，ViewModel 通过 `ViewModelProvider.Factory` 取值）；
2. **Hilt**（androidx.hilt 1.4.0 + Dagger 2.60.1，编译期注解处理，需 KSP 与 `hilt-android-gradle-plugin`，Gradle 插件要求 AGP 9+）；
3. **Koin**（运行时 DSL 容器）。

约束：项目定位轻量极简；项目维护者编程经验有限（教学级可读性与排错体验权重高）；MVP 为单人维护；依赖对象规模可枚举。

## Decision

**采用手动 DI（AppContainer 模式）**，不引入任何 DI 框架。

具体形态（规则）：

1. `TimetableApp`（Application）持有唯一 `AppContainer` 实例，负责构造数据库、DataStore、OkHttp、各仓库实现；`AppContainer` 内为惰性单例（`by lazy`），总行数控制在 100 行以内。
2. ViewModel 通过自定义 `ViewModelProvider.Factory`（或在 Compose 侧用 `viewModel(factory = ...)`）从容器取依赖；禁止 ViewModel 内 `new` 出仓库或直接访问 `Context` 应用级单例（在 `AndroidViewModel` 里兜底访问 Application 也不允许）。
3. 依赖关系以构造参数显式声明，禁止服务定位器式的全局可变单例（除 AppContainer 本身外）。

## Consequences

### 正面

- **零框架成本**：无注解处理器、无额外 Gradle 插件、无运行时依赖，构建时间与 APK 体积为零负担（与极简定位一致）。
- **可读性最高**：全部装配关系集中在一个普通 Kotlin 文件里，新手可以逐行读懂"谁依赖谁"，这是教学级项目的核心价值。
- **排错路径最短**：不会出现 Dagger 那种多轮生成的、难以定位的编译错误链。
- **迁移路径已预置**：仓库以接口暴露（见架构文档 §8.1），未来迁 Hilt/Koin 只改装配层与 ViewModel 注解，业务代码不动。

### 负面 / 代价

- 依赖增多时装配代码线性增长，`AppContainer` 会变长（缓解：超过 100 行即为拆分的信号；当前依赖对象 < 15 个）。
- 无编译期依赖图校验，"忘记装配某个依赖"只能在运行期暴露（缓解：MVP 期间为单一装配点，漏装配会在首次启动即崩溃，不会潜伏）。
- 测试替换需要手工构造假实现（缓解：仓库接口边界清晰，手工注入 fake 即可，反而比注解框架更直观）。

### 迁移触发条件（写入本 ADR，届时应新开 ADR）

出现以下任一信号时，重新评估迁移到 Hilt，并新开 ADR 记录：

- ViewModel 数量超过 8 个，或 `AppContainer` 超过 120 行；
- 项目进入多人协作（装配冲突开始发生）；
- 需要 Hilt 生态的既有集成红利（如 `@HiltWorker` 的 WorkManager 自动注入在 Worker 数量增多时收益显现）。

当前基线（5–6 个 ViewModel、< 15 个依赖对象）距该阈值有明显余量，MVP 阶段引入 Hilt 属过度设计。

### 已否决选项的代价说明

- **Hilt**：编译期安全与规模化能力是真实优势，但代价是三层新概念（注解 / Component / Scope）与陡峭的报错曲线，对单人新手项目收益为负；且其 Gradle 插件要求 AGP 9+ 与 KSP 链路，增加了构建配置的故障面。
- **Koin**：DSL 直观，但错误在运行期才暴露，与"新手排错友好"目标相反，且引入运行时依赖。
