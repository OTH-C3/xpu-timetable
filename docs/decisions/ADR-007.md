# ADR-007: MVP 采用单模块 + 分层分包，拒绝多模块 Clean Architecture

- **Status**: Accepted (2026-09-16)
- **Date**: 2026-09-16
- **Deciders**: 项目维护者
- **Related ADRs**: ADR-004（手动 DI 的可行性前提）、ADR-006（解析器隔离的落点）、ADR-009（版本基线）

## Background

工程结构要在"可维护性"与"认知成本"之间取舍。候选：

1. **单 Gradle 模块（`:app`）+ 包分层**：一个模块内按 `ui / domain / data / importer / parser / reminder / widget` 分包，依赖方向靠约定与代码审查保障；
2. **多模块 Clean Architecture**：`:app / :core:model / :core:data / :feature:timetable / :parser-xpu` 等，依赖由 Gradle 强制；
3. **按功能垂直切分的 feature 模块**：每个页面一个模块。

参考事实：竞品 Dawn Course（HF-CYGG/Dawn-Course）采用多模块 Clean 架构 + 独立服务端，但它是团队协作、含服务端的产品；Sleepy 课程表（定位最接近本项目）为轻量本地优先形态。本项目为单人维护、MVP 五项功能、代码量预计数千行级。

约束：项目维护者编程经验有限；极简轻量与"打开即快"是产品定位；开源社区可读性重要。

## Decision

**MVP 采用单 Gradle 模块 `:app` + 分层分包**，依赖方向由架构文档 §2.1 的铁律约束，并通过自检门禁（静态 import 检查）保障。

分包结构（规则，详见架构文档 §6.2）：`di / domain / data / importer / parser / reminder / widget / ui`。

例外说明：Baseline Profile（v1.1 性能任务）所需的 `:baselineprofile` 模块属于构建基建（instrumented test 模块），不承担业务代码，**不违反本决策**。

### 拆模块的触发条件（预置，届时新开 ADR）

当且仅当出现以下任一信号时，把 `parser/` 拆为独立模块 `:parser-xpu`（其余保持不动）：

- 需要适配第二所学校（`parser/` 出现多实现并存的真实需求）；
- 主工程构建时间超过 1 分钟且增量编译明显劣化。

当前无任一信号成立，提前拆分属过度设计。

## Consequences

### 正面

- 认知成本最低：新手只需理解一个模块的目录结构，不需要先学 Gradle 多模块依赖声明、`:core` 与 `:feature` 的依赖倒置技巧。
- 构建最快（单模块增量编译链最短），与"打开即快"的迭代节奏一致；配置故障面最小。
- 与手动 DI（ADR-004）天然匹配：装配点唯一，依赖关系在一个文件内可见。
- 解析器隔离目标（ADR-006）靠**包边界 + 接口边界**同样达成：改版适配只改 `parser/xpu`，该约束由代码审查与文件范围界定，而非 Gradle 强制——对本项目的单人规模，包边界足够。

### 负面 / 代价

- 依赖方向靠约定而非编译器强制，存在被无意违反的可能（缓解：自检门禁用静态 import 检查兜底——ui 不得 import Room/DataStore/webkit，data 不得 import Compose；见架构文档 §12 第 3 步）。
- 模块级并行开发能力弱（缓解：单人项目无此需求）。
- 未来若迁移多模块，需要一次集中的结构调整（缓解：分包边界已按未来模块边界设计，迁移主要是搬运与声明，不涉及重写）。

### 已否决选项的代价说明

- **多模块 Clean Architecture**：其收益（强制边界、团队并行、按需编译、可复用 core）在单人 MVP 上几乎全部闲置，代价却是即时发生的：Gradle 配置复杂度、模块间 API 暴露管理、新手排错难度上升。竞品采用它是团队与产品规模驱动，不是"更好的通用答案"。
- **feature 垂直模块**：页面数量（4 个）远未达到需要隔离的规模，且垂直切分与解析器隔离（本项目的核心维护面）正交，无收益。
