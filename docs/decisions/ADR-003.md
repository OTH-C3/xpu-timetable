# ADR-003: 使用 Room 3 + DataStore 作为本地存储

- **Status**: Accepted (2026-09-16)
- **Date**: 2026-09-16
- **Deciders**: 首席架构师（高见远）；待发起人确认
- **Related ADRs**: ADR-001（Compose）、ADR-005（网络与解析）、ADR-007（单模块结构）

## Background

本项目是纯本地 App（无后端、无云同步），全部数据必须妥善落在设备本地。数据分两类，性质完全不同：

1. **课表数据**：课程 × 上课安排 × 学期 × 周次 × 节次的关系型数据，查询形态是"给定学期与周次，取某天/整周的全部课程安排"，还要支持单双周与起止周过滤、去重合并。特点是结构化、关系明确、查询条件组合多。
2. **用户偏好**：提醒开关、提前分钟数、当前周手动校正值等少量键值，读写简单、无查询需求。

候选方案：

- Room（Android 官方 ORM，当前主版本 Room 3，坐标 `androidx.room3`，2026-07 stable，2026-09-09 最新 stable 3.0.3）；
- SQLDelight（SQL 优先的跨平台方案）；
- DataStore-only（用键值/序列化对象存全部数据）。

技术上必须同时满足：响应式查询（数据变更自动推送 UI/小组件/提醒调度）、事务写入（一次导入必须原子完成）、编译期校验（新手最怕运行期才发现 SQL 写错）。

## Decision

**双轨存储**：

- **Room 3.0.3（`androidx.room3:room3-runtime` / `room3-compiler`，KSP 处理）承担课表结构化数据**（terms / courses / course_sessions / time_slots / import_logs 五表，Schema 见架构文档第 7 章）；
- **DataStore Preferences 1.2.1 承担用户偏好**（UserPreferencesStore，见架构文档 §8.3）。

Room 3 使用要点（必须遵守，均为与 Room 2 的破坏性差异）：

1. 坐标与包名变更：`androidx.room:room-*` → `androidx.room3:room3-*`，`androidx.room.*` → `androidx.room3.*`；
2. **仅支持 KSP**，禁止 KAPT 配置；
3. DAO 函数必须为 `suspend` 或返回 `Flow`（Room 3 全面协程化，同步 DAO 不支持）；
4. 事务 API 由 `runInTransaction {}` 变为 `withWriteTransaction {}`；`@TypeConverter` 更名为 `@ColumnTypeConverter`；
5. 必须使用 `androidx.room3` Gradle 插件并配置 `schemaDirectory`，导出的 schema JSON 提交仓库（自动迁移与校验的依据）。

## Consequences

### 正面

- 编译期 SQL 校验：DAO 查询在构建阶段被注解处理器验证，把"SQL 写错"从运行期崩溃提前到编译失败，对新手排错最友好。
- `Flow` 原生集成：课表变更自动驱动周视图、桌面小组件、提醒调度刷新，全链路无手写事件通知（与 ADR-001 的 Compose 状态驱动直接契合）。
- 关系建模直接落地"课程—上课安排"拆分，避免把周次/节次过滤逻辑写成手写 Kotlin 过滤。
- schema 导出 + `AutoMigration` 路径为 v2 之后的数据演进留好出口。

### 负面 / 代价

- **网络上绝大多数 Room 教程是 Room 2.x 写法，与本项目不兼容**（KAPT、同步 DAO、旧包名、`runInTransaction`）。这是本项目教学文档必须前置说明的最大知识型坑，生成式代码与检索式排错都极易踩中。
- Room 3 移除了 SupportSQLite API：若未来引入仍依赖 `SupportSQLiteDatabase` 的第三方库会冲突（缓解：本项目不引入此类库；万不得已可加 `room3-sqlite-wrapper` 兼容层，但视为技术债）。
- 破坏性迁移策略在 MVP 期被允许（本地数据可由重新导入恢复，避免新手维护迁移 SQL）；**自 v2 起禁止使用 `fallbackToDestructiveMigration`，必须提供 AutoMigration**——该触发条件在本 ADR 登记，届时须新开 ADR 记录迁移方案。
- 双轨存储意味着两套 API 心智（Room + DataStore），但各自边界清晰（结构化数据 vs 键值偏好），实际认知负担低。

### 已否决选项的代价说明

- **SQLDelight**：能力与 Room 相当，跨平台更优，但本项目无跨平台需求；Room 在 Android 官方文档、AS 工具链、社区覆盖上优势更大，且 SQLDelight 的 KMP 概念对新手是额外负担。
- **DataStore-only**：无法表达关系查询，周次/节次过滤需全量读取后在内存手写过滤，数据量与查询复杂度稍增即劣化；且无事务、无编译期校验。仅键值偏好适合 DataStore。

## 后续修订记录（活规格）

**2026-09-16 — 学期归属补入（Spec AC-13 驱动）**

- 修订内容：`courses` 表新增 `term_id`（INTEGER NOT NULL，FK → terms.id，ON DELETE CASCADE）+ `index_courses_term_id`；`TimetableRepository.observeWeek(termId, week)` 的 `termId` 成为必填过滤条件；`applyImport` 的学期解析规则显式化（parser 产出的 term 优先，回退激活学期，两者皆无则返回 `ValidationFailed`，禁止静默创建学期）。
- 动机：原 Schema 以 `course_sessions` 为学期关联锚点，无法表达"一门课属于哪个学期"这一课程级事实，导致"不同学期课程串台显示"与"重复导入无法按学期覆盖"两个验收点无法实现。
- 影响面：仅数据层 Schema 与仓库签名；`parser`、`ui` 层不受影响（领域模型 `ParsedSchedule.term` 原本已预留学期信息）。UI 侧新增义务：导入预览页必须显示目标学期并允许纠正（架构文档 §8.2）。
- 迁移影响：无。首个公开版本尚未发布，本次修订折叠进 v1 初始 Schema，不产生 Room 迁移；7.4 节的迁移策略不变。
- 相关文档同步：架构文档 §7.1 / §7.2 / §7.3 / §7.4 / §8.1 / §8.2 / §9.2 已同步。

**2026-09-16 — AC-13 写入语义裁决：覆盖按导入来源切分，MANUAL 永不被删除（team-lead 裁决）**

- 修订内容：
  1. `applyImport` 的替换范围按来源切分——删除条件为 `(term_id = 目标学期 AND source = 本次导入来源)`，Web 只替换 `WEB`、CSV 只替换 `WAKEUP_CSV`，禁止跨来源删除；
  2. 新增不变量（P0）：`source = MANUAL` 的课程**永不被任何导入删除**；
  3. 同源重复导入必须幂等（不产生同源重复累积）；
  4. 疑似重复（与手动课程同名）**只提示、不自动合并**；
  5. `ImportSummary` 必须回传三类计数：`replacedCount` / `preservedManualCount` / `suspectedDuplicateCount`；`import_logs` 增列 `replaced_count`、`preserved_manual_count`。
- 动机（数据安全的不对称性）：静默删除用户手工录入的课程是**不可逆**的数据丢失；而跨来源重复项是可逆的、用户可见且可自行清理。两者代价不对称，因此取"保留"而非"清空"。此外 Spec §10 已有"导入失败绝不破坏已有本地数据"的稳定性要求，"整学期全删重插"与之一致性冲突。
- 影响面：数据层 SQL 的删除条件与 `ImportSummary` 类型；UI 层导入预览页与结果页（依赖三个计数渲染覆盖范围与疑似重复提示）。`parser` 层不受影响。
- 迁移影响：无（沿用 v1 初始 Schema 折叠策略；`import_logs` 新增两列同属发布前修订）。
- 关联验收：AC-13（覆盖范围提示 + 按来源替换 + 无同源重复累积）、AC-20（P0，MANUAL 课程必须完整保留）、AC-21（P1，同名疑似重复提示，不做自动合并）。
- 相关文档同步：架构文档 §7.2（import_logs 增列）、§8.2（扩写为「学期归属 + 写入归属」三部分）、§9.1 第 8 步（预览页内容）已同步。

**2026-09-16 — 编辑归属裁决：用户编辑过的课程转 MANUAL 并记录 edited_at（team-lead 裁决）**

- 修订内容：
  1. `courses` 增列 `edited_at`（INTEGER NULL）——用户手动编辑时间戳；
  2. 新增不变量（P0，AC-22）：用户手动编辑过的课程，`source` 必须置为 `MANUAL` 且记录 `edited_at`，此后任何来源的导入不得删除它；
  3. domain 层新增纯函数 `Course.markEdited(nowMillis)`（返回 source=MANUAL、editedAt=now 的副本，对 MANUAL 课程幂等），作为 UI 编辑路径的唯一入口；UI 禁止自行 `copy(source = MANUAL)`；
  4. `Course` 领域模型补 `editedAt: Long?` 字段（架构文档 §8.1 契约要点 4）。
- 动机：**消除一条无提示的数据丢失路径**。在"按来源替换"机制下，若用户编辑后保留原 `source`（如 `WEB`），下次同源导入会把该课程当同源记录整体替换，用户的改动被静默清除；且用户不会预期"我改过的课会消失"，仅在预览页给泛泛提示不足以防住。置 MANUAL 的代价（可能与导入记录同名重复）是可见、可逆、可由用户自行清理的（AC-21 已要求提示），与静默丢失的不可逆后果不对称，故取此侧。同时以 `edited_at` 保留"该课程曾来自导入且被修改过"的溯源信息，避免该事实永久丢失。
- 影响面：`courses` 表加列、`Course` 领域模型加字段、domain 增纯函数、UI 编辑路径（必须走 `markEdited`）、导入计数（编辑过的课程自此刻起计入 `preservedManualCount`）；`import_logs` 表加列（`replaced_count` / `preserved_manual_count`，与上一次修订同批）。`parser` 层不受影响。
- 迁移影响：无（同为发布前 v1 初始 Schema 内的折叠修订，无存量库需升级）。
- 关联验收：AC-20（MANUAL 必须保留）、AC-21（疑似重复提示，不自动合并）、AC-22（P0，编辑后转 MANUAL + 记录 edited_at + 后续导入不得删除）。
- 相关文档同步：架构文档 §7.2（courses 增 `edited_at`；import_logs 增两列）、§8.1（Course 字段清单 + 编辑路径约束）、§8.2 第 10 条（编辑归属不变量 + markEdited 纯函数）已同步。
- 未采纳项：team-lead 未采纳"预览页按来源分列显示各类数量"的附加建议（预览页已有覆盖范围说明 + 疑似重复提示，再分列会信息过载），改由 UI 阶段按实际版面判断——本 ADR 记录该取舍，避免后续被重新提出。
