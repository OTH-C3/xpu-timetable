# ADR-006: 教务数据捕获采用混合策略（shouldInterceptRequest 为主，evaluateJavascript 降级）

- **Status**: Accepted (2026-09-16)
- **Date**: 2026-09-16
- **Deciders**: 首席架构师（高见远）；方向继承 Phase 0 决策（WebView 授权登录 + 解析），本 ADR 决定其工程实现策略
- **Related ADRs**: ADR-005（OkHttp，策略 A 的代发客户端）、ADR-007（解析器隔离结构）、ADR-008（导航，导入页入口） 

## Background

Phase 0 已锁定：数据获取主路径为「App 内 WebView 授权登录 sz.xpu.edu.cn → 解析课表 → 本地入库」，凭据零存储零上传是隐私红线；兜底为 WakeUp CSV / 手动添加。本次要决定的是**"如何从 WebView 会话中把课表数据取出来"**这一工程策略问题。

关键已知事实与约束：

- 一网通办登录含滑块/点选验证，登录必须由用户在 WebView 内手动完成，App 对凭据与验证过程零接触（这同时排除了纯 HTTP 模拟登录）。
- 「我的课表」是 SPA 页面，**接口路径、请求方法（GET/POST）、响应 JSON 结构均未知**，需一次真机抓包确定（Phase 0 OPEN #2）。这是本 ADR 必须在"信息不完整"下做决策的原因。
- 学校改版是**确定会发生**的维护事件（Phase 0 已列风险 #1），策略选择必须考虑改版后的可诊断性与降级体验。

候选策略：

1. **A：`shouldInterceptRequest` 拦截 XHR/JSON**。WebView 的所有资源请求（含 fetch/XHR）都经该回调；命中特征后由 OkHttp 代发，响应体分流：一份包装为 `WebResourceResponse` 回给 WebView 正常渲染，一份交解析器。
2. **B：`evaluateJavascript` 注入抓 DOM / hook fetch**。页面加载完成后注入 JS，或以 `JavascriptInterface` 回传从 DOM 序列化出的课表数据。
3. **C：纯 Cookie 复用直连**。WebView 登录后从 `CookieManager` 取会话 Cookie，OkHttp 直接请求课表接口。

## Decision

**采用混合策略：A 为主策略，B 为降级策略；C 不纳入 MVP 主路径。**

工程规则：

1. 策略 A 先判定、先执行；未命中特征或解析失败时，自动转入策略 B，无需用户干预。
2. 两条策略产出统一汇入 `WebImportCoordinator.resolve()` → `XpuJsonParser` / `XpuDomParser` → `ParsedSchedule`，下游（仓库/UI）不感知数据来自哪条策略。
3. 特征匹配规则集中定义在 `parser/xpu/XpuEndpoints.kt`（唯一改版适配点）；特征匹配失败必须能在日志中区分"未命中"与"命中但结构变化"两种情形（对应 `CaptureMissed` 与 `ParseError.SchemaMismatch`）。
4. 兜底通道（WakeUp CSV / 手动添加）在任何情况下保持一级入口可用；主通道失败必须给出明确降级提示，**App 永不因主通道失效而不可用**。
5. 隐私红线（不可裁剪）：凭据零读取零存储零上传；`dataExtractionRules`/`fullBackupContent` 排除 WebView 数据与 Cookie（防止 SSO 会话 Cookie 被自动备份上云）；Release 关闭 `WebContentsDebuggingEnabled`；禁止任何验证码自动绕过实现。

## Consequences

### 正面

- A 拿到的是一手 JSON，与页面渲染实现解耦，是学校"改前端不改接口"这类改版下最稳的一层（课表类第三方工具社区的主流做法）。
- B 覆盖 A 的结构性盲区：接口未知、或接口形态是 POST 时仍有数据通路。
- 双策略共享下游，改版诊断有明确信号：`CaptureMissed`（拦不到）与 `SchemaMismatch`（结构变了）直接指向两类不同的适配工作，避免"导入失败"这类无信息量报错。
- 与隐私红线完全兼容：WebView 方案下验证码/滑块是用户的正常操作，不需要也不允许任何绕过手段。
- 开发顺序上可先交付兜底通道（CSV/手动），主通道的抓包未知不阻塞整体进度。

### 负面 / 代价（真实限制，编码时不得"假装不存在"）

- **`shouldInterceptRequest` 拿不到 POST 请求体**——`WebResourceRequest` 不暴露请求体，因此"代发"只对 GET 类请求成立。若课表接口是 POST，策略 A 只能原样放行并转策略 B。这是选择混合策略而非单策略的直接原因。
- 策略 B 强依赖页面 DOM 结构或前端框架行为（hook fetch/XHR 需要页面自身实现可被覆写），学校前端重构即失效；注入时机（`onPageFinished` / 轮询 / 变脸观察）需要调试，存在时序脆弱性。
- 双策略带来约两倍的解析适配代码与测试面（缓解：两条解析路径共用领域模型与校验逻辑，测试以抓包金样本 fixture 驱动）。
- 策略 C 未纳入：接口可能要求页内 token/自定义请求头/Referer 校验，未知项过多，MVP 不做；若抓包后验证可行，可作为策略 A 的简化实现形式在 v1.1 引入（需新开 ADR）。
- WebView 登录态默认不跨会话持久，MVP 不承诺"免二次登录"，导入页文案不得暗示持久登录。

### 失败模式与必须的降级行为（与架构文档 §9.1 表对应）

| 注入点 | 必须行为 |
|--------|----------|
| 站点不可达（校外/校园网限制） | 提示网络可达性受限，引导更换网络环境重试 |
| 会话失效（拦到登录页 HTML） | `NotLoggedIn`，提示重新登录 |
| 未命中特征（改版） | 超时后转 B；B 失败 → `CaptureMissed` → 降级提示 + 引导兜底通道 |
| 结构变化 | `ParseError.SchemaMismatch` → "教务系统疑似改版"提示 + `import_logs` 记录 detail |
