## 0. 阅读方式（给项目维护者的教学级说明）

这份文档回答三个问题：

1. **用什么技术**（第 3、4 章）——每个选型都给了至少 3 个候选的对比表，以及"为什么选它、不选另外两个会怎样"。
2. **代码怎么组织**（第 5、6、7 章）——解析器隔离设计是本项目最重要的架构决策，因为学校教务系统随时可能改版，架构必须保证"改版只改一处"。
3. **模块之间怎么协作**（第 8、9 章）——本项目是纯本地 App，没有后端、没有 REST API。"接口契约"在这里指的是 **Kotlin 接口签名**：上层代码只允许通过这些签名调用下层，不允许绕过。

阅读顺序建议：先看第 1 章结论速览，再按需深入。每条关键决策都有对应的 ADR 文档存放完整背景与取舍。

**文档中「规则」与「示例」的区分**：本文凡写"必须/禁止"的是规则，违反即不合格；凡写"例如/可以这样"的是示例，可按实际情况调整。两者不混写。

## 2. 架构总览

### 2.1 分层架构（依赖只能向下）

```
┌─────────────────────────────────────────────────────────┐
│ 表现层 ui/                                                │
│   Compose 界面 + ViewModel + Navigation 3                 │
│   只做：状态收集、用户事件分发、界面渲染                    │
├─────────────────────────────────────────────────────────┤
│ 领域层 domain/                                            │
│   纯 Kotlin 数据模型 + 仓库接口（无 Android 依赖）          │
│   只做：定义业务数据形状与规则（周次计算、单双周判断）        │
├─────────────────────────────────────────────────────────┤
│ 数据层 data/                                              │
│   Room 数据库 + DataStore + 仓库实现                       │
│   只做：数据读写、事务、Flow 暴露                          │
├─────────────────────────────────────────────────────────┤
│ 基础设施 importer/ parser/ reminder/ widget/              │
│   WebView 捕获会话、教务解析器、提醒调度、桌面小组件         │
│   产出领域模型，经仓库接口入库                              │
└─────────────────────────────────────────────────────────┘
```

**铁律**（出现即不合格）：

- 依赖只能向下：`ui → domain ← data/infrastructure`。ui 禁止直接 import Room/DataStore/WebView 类型。
- ViewModel 禁止直接操作数据库，必须经仓库接口。
- 仓库实现（data 层）禁止 import Compose 类型。
- `parser/` 与 `importer/` 只产出 domain 模型，禁止直接写数据库（必须经仓库）。

### 2.2 模块图（MVP：单 Gradle 模块 + 包隔离）

```
:app （唯一 Gradle 模块）
└── com.xpu.timetable
    ├── TimetableApp.kt        Application，只装配 AppContainer
    ├── MainActivity.kt        入口，只 setContent + 主题 + 导航
    ├── di/                    AppContainer（手动 DI 唯一装配点）
    ├── domain/model/          Course、CourseSession、Term、TimeSlot…
    ├── domain/repository/     TimetableRepository 等接口
    ├── data/db/               AppDatabase、Entity、Dao、迁移
    ├── data/repository/       仓库实现
    ├── data/transfer/         课表 JSON 编解码与二维码（M6）
    ├── importer/api/          ScheduleImporter 接口与 ImportResult
    ├── importer/xpu/          教务直连通道（WebView 抓取 → 解析 → 入库）
    ├── importer/file/         本 App 导出的 .json / 二维码导入（M6）
    ├── parser/api/            PayloadParser 接口与解析结果类型
    ├── parser/xpu/            西工程大专用解析器 + 端点配置（改版只改这里）
    ├── widget/                Glance 桌面小组件（含闹钟恢复接收器）
    └── ui/                    theme / navigation / 各页面 / components
```

完整目录约束见第 6 章。多模块化是规模化后的形态，MVP 阶段照抄属过度设计（依据与触发拆分的条件见 ADR-007）。

### 2.3 数据流总图

```
【导入主通道】
 用户 → WebView 登录 sz.xpu.edu.cn（滑块/扫码由用户手动完成，App 零接触凭据）
      → shouldInterceptRequest 拦截课表 XHR/JSON 响应（策略 A）
        （未命中 → evaluateJavascript 抓取 DOM/接口数据，策略 B）
      → 原始载荷 RawPayload(String)
      → parser/xpu 解析 → ParsedSchedule（领域模型）
      → TimetableRepository.applyImport()（事务：写入 courses/course_sessions + import_logs）
      → Room 数据变更 → Flow 自动推送 → 界面/小组件刷新

【导入兜底通道】（接口未知或学校改版时保证 App 可用闭环）
 本 App 导出的 .json / 二维码截图 → importer/file → parser（JSON）→ 同一仓库入口 applyImport()
 手动添加/编辑 → ui/courseedit → 仓库 upsertCourse()/deleteCourse()
 （M9 已删除 WakeUp CSV 通道：产品负责人裁定该兜底路径不再提供）

【课表显示】
 TimetableViewModel → repository.observeWeek(termId, week) → Flow<WeekSchedule> → 周视图渲染

【桌面小组件】
 导入完成/设置变更 → WidgetRefresher.refreshAll() → Glance 重绘
   跨天 00:05（requestCode 4003）与每节课结束（4002）各排一条精确闹钟兜底
 （M7 已整体移除课前提醒：reminder/ 包与其偏好层、通知权限一并删净）
   → Notification（Android 13+ 需运行时申请 POST_NOTIFICATIONS）

【桌面小组件】
 Glance 小组件订阅仓库 Flow → 数据变更/定时刷新 → 桌面卡片更新
```

## 3. 技术选型对比矩阵

评分标准：五星制。权重按本项目定位（轻量、无后端、项目维护者编程经验有限、开源可维护）设定，与通用商业项目不同——**学习成本与维护成本权重高，扩展性权重低**。

### 3.1 UI 框架

| 候选 | 开发效率 | 新手友好度 | 生态/文档 | 课表场景适配 | 结论 |
|------|----------|-----------|-----------|--------------|------|
| Jetpack Compose (Material 3) | 5/5 | 4/5 | 5/5（官方第一优先） | 5/5（声明式网格/周视图自定义自由度高） | **推荐** |
| 传统 View + XML | 3/5 | 3/5（布局/代码分离双语言） | 4/5（存量教程多但已停更方向） | 3/5（自定义周视图需自绘 View，门槛更高） | 不选 |
| Compose + View 混合 | 2/5 | 2/5（需同时掌握两套） | 3/5 | 2/5 | 不选 |

**决策**：Compose（ADR-001）。关键依据：

- 2026 年官方所有新文档、新组件、Codelab 均以 Compose 为第一公民；竞品 Sleepy、Dawn Course 全部是 Compose。
- 本项目周视图是高度自定义 UI，Compose 的自定义 Layout/Canvas 比 XML 体系（自绘 View + invalidate 手动管理）代码量少得多。
- 混合方案是迁移期产物，新项目没有任何理由引入两套心智模型。
- **不选 View/XML 的代价说明**：存量第三方教程更多是它唯一的优势，但方向已死，学到的 XML 技能在两年后的生态里持续贬值。

### 3.2 图标库（P0 规则落地项）

项目级 P0 规则：全项目锁定**一套** SVG 图标库，禁止 emoji 图标，禁止混用多套图标。尺寸规范 16/20/24（dp，对应小/中/标准三档）。

| 候选 | 描边/风格统一性 | 接入方式 | 体积控制 | 维护度 | 结论 |
|------|----------------|----------|----------|--------|------|
| Lucide（compose-icons 2.2.1） | 5/5（单一风格：24px 网格、2px 等宽描边，无填充/线性变体混淆） | 一个 Gradle 依赖，`R.drawable` 直接引用 | 4/5（约 1600 图标，配 R8 资源收缩后只保留实际引用） | 4/5（Composable Horizons 维护，2026 年持续发版，MIT 协议） | **推荐** |
| Material Symbols（官方推荐方向） | 4/5（需每次下载时手动统一 weight/fill/grade 参数，人工纪律保障一致性） | 无官方 Compose 库；官方路径是逐个从 Google Fonts 下载 VectorDrawable XML 放入 res/ | 5/5（只用多少下多少） | 5/5（Google 官方） | 备选 |
| Phosphor | 4/5 | 无成熟 Compose 一等库（社区移植陈旧） | — | 2/5 | 不选 |
| androidx material-icons-core/extended | — | — | — | **已冻结 1.7.8，已从 Material 3 移除，官方弃用** | 禁止 |

**决策**：Lucide（ADR-002）。关键理由：

- **工程确定性强**：Material Symbols 官方路径要求"每个图标去网页下载一次并人工保持参数一致"，对单人维护的开源项目是持续的认知负担，风格漂移风险由人工纪律兜底；Lucide 单一风格从机制上消灭了变体混用问题。
- **坐标已核实存在**：`com.composables:icons-lucide-android:2.2.1`（2026-09-16 于 composables.com / klibs.io 核实），Android 变体以 VectorDrawable XML 交付。
- **锁定不锁死**：所有图标引用收敛到 `ui/components/AppIcons.kt` 一个门面文件（语义名到资源的映射）。未来若需换库，只改这一个文件，这是对"锁定一套"的架构性保障。

**落地规则（必须遵守）**：

- 图标尺寸只允许三档：16dp（列表次要信息）、20dp（导航/按钮）、24dp（工具栏/标准）。在 `ui/theme/IconSize.kt` 定义常量，禁止散落魔法数字。
- 禁止在字符串、按钮文本、通知文案中使用 emoji 代替图标。
- 通知图标（Android 要求白色剪影小图）走单独的 `res/drawable/ic_stat_*` 通知专用图，与界面图标体系分离（这是系统要求，不属于混用）。

### 3.3 本地存储

| 候选 | 类型安全 | 学习成本 | 与 Flow/协程集成 | 课表数据适配 | 结论 |
|------|----------|----------|------------------|--------------|------|
| Room 3.0.3 | 5/5（编译期 SQL 校验） | 3/5 | 5/5（Room 3 全面协程化） | 5/5（课程/节次/周次关系型查询） | **推荐**（课表数据） |
| SQLDelight | 5/5 | 3/5（SQL 优先 + KMP 概念） | 4/5 | 4/5 | 不选 |
| DataStore-only | 2/5（自己写序列化与查询） | 2/5 | 5/5 | 2/5（课表是关系型数据，手写过滤周次/节次极痛苦） | 不选（仅用于偏好设置） |

**决策**：Room 3 + DataStore 双轨（ADR-003）：

- 课表数据（结构化、需要按周次/星期/节次查询）→ Room。
- 用户偏好（提醒提前分钟数、主题选项、当前学期等少量键值）→ DataStore Preferences 1.2.1。
- **Room 3.0 迁移要点（2026-07 发布，与网上大量 Room 2.x 教程不兼容，必须知晓）**：
  - 新坐标 `androidx.room3:room3-runtime` / `room3-compiler`，新包名 `androidx.room3.*`；
  - 仅支持 KSP（禁 KAPT），DAO 函数必须是 suspend 或返回 Flow；
  - `runInTransaction {}` 改为 `withWriteTransaction {}`；`@TypeConverter` 更名为 `@ColumnTypeConverter`；
  - 必须使用 `androidx.room3` Gradle 插件配置 `schemaDirectory`，schema JSON 入库用于自动迁移。
- **为什么不用 SQLDelight**：能力相当，但 Room 是 Android 官方第一公民、AS 模板/文档/社区覆盖更广，对新手排错友好。
- **为什么不用 DataStore 存课表**：课表查询本质是关系查询（"第 3-18 周、单周、周三 5-6 节"），键值模型会把过滤逻辑全部推到手写 Kotlin 代码里，性能与可维护性双输。

### 3.4 依赖注入

| 候选 | 学习曲线 | 编译期安全 | 构建复杂度 | MVP 规模适配 | 结论 |
|------|----------|-----------|-----------|--------------|------|
| 手动 DI（AppContainer） | 5/5（就是普通 Kotlin 类） | 3/5（靠人肉） | 零额外依赖、零注解处理器 | 5/5（本 App 依赖对象 < 15 个） | **推荐** |
| Hilt (androidx.hilt 1.4.0 + Dagger 2.60.1) | 2/5（注解、Component、Scope 三层概念；Dagger 报错信息出名地难懂） | 5/5 | +1 注解处理器（KSP），AGP 9 兼容已就绪 | 3/5 | 备选（规模化后迁移） |
| Koin | 4/5（DSL 直观） | 2/5（运行时才报错） | +1 运行时依赖 | 4/5 | 不选 |

**决策**：手动 DI（ADR-004）。关键理由：

- 本 App 的依赖图非常小：1 个数据库、1 个 DataStore、1 个 OkHttp、3-4 个仓库、5-6 个 ViewModel。一个 `AppContainer` 类（约 100 行以内）即可表达全部装配关系，**看得见摸得着，对新手是最重要的教学属性**。
- Hilt 的价值（大规模依赖图 + 团队协作 + 自动化测试替换）在单人 MVP 里完全用不上，却要付出注解处理器构建时间与陡峭排错曲线。
- 迁移路径已预置（ADR-004）：当出现"ViewModel 超过 8 个 / 开始多人协作"触发条件时迁移 Hilt，仓库接口边界保证迁移只改装配层。
- Koin 的运行时报错特性与"新手排错"诉求相反，直接排除。

### 3.5 网络与 JSON 解析

本项目网络需求极小且特殊：**唯一的网络交互发生在 WebView 里**（用户登录 + 页面加载由系统 WebView 完成）。OkHttp 的角色仅是导入主通道的辅助（拦截器内代发请求与响应分流，见 3.6）。

| 候选 | 包体积 | 学习成本 | 本场景适配 | 结论 |
|------|--------|----------|-----------|------|
| OkHttp 5.4.0 + kotlinx-serialization 1.11.0 | 小 | 4/5 | 5/5（拦截器场景只需裸客户端 + 手写 DTO 解码） | **推荐** |
| Retrofit + converter | 中 | 3/5 | 2/5（接口式封装服务的是"多端点 REST API"，本项目端点未知且只有一个，抽象层为负资产） | 不选 |
| Ktor Client | 中 | 3/5 | 3/5（功能全但 JVM/Android 依赖树更重，杀鸡用牛刀） | 不选 |

**决策**：OkHttp 5.4.0 + kotlinx-serialization-json 1.11.0（ADR-005）。注意 kotlinx-serialization 需要同时加 Gradle 插件 `org.jetbrains.kotlin.plugin.serialization` 与 Kotlin 版本对齐（1.11.0 基于 Kotlin 2.3.20 编译，见 4.2 的版本链约束）。JSON DTO 全部用 `@Serializable` data class 定义在 `parser/xpu/dto/`，`ignoreUnknownKeys = true` 必须开启（教务接口字段未知，未知字段容忍是硬要求）。

### 3.6 WebView 课表捕获策略（本项目最高风险项）

三种可选策略，推荐**混合：A 为主、B 降级**（ADR-006）。

| 策略 | 原理 | 优点 | 失败模式 | 结论 |
|------|------|------|----------|------|
| A. shouldInterceptRequest 拦截 XHR/JSON | WebView 的所有资源请求（含 fetch/XHR）都经过该回调；命中课表接口特征时，代为请求并分流响应体：一份回给 WebView 正常渲染，一份交给解析器 | 拿到原始 JSON，结构与 UI 渲染无关，最稳定；不依赖页面加载时机 | ① POST 请求体在 `WebResourceRequest` 中不可见——若课表接口是 POST，无法代发，只能原样放行并转策略 B；② 需先抓包确定接口 URL 特征，否则不知道拦谁 | **主策略** |
| B. evaluateJavascript 注入抓 DOM/数据 | 页面加载完成后注入 JS：优先 hook `fetch`/`XMLHttpRequest` 复述响应，或直接读取已渲染课表 DOM 序列化为 JSON 回传（JavascriptInterface） | 不需要预知接口路径；DOM 方案对"接口改了但页面还在"的改版有韧性 | 强依赖页面 DOM 结构/前端框架行为；时机控制复杂（需 onPageFinished + 轮询/变脸观察）；学校前端重构即失效 | **降级策略** |
| C. 纯 Cookie 复用直连 | WebView 登录后从 CookieManager 取会话 Cookie，OkHttp 直接请求课表接口 | 链路最短 | 接口可能要求页内 token/自定义头/Referer 校验，未知字段全靠抓包试错；登录态判断复杂 | 不做主路径（抓包后若验证可行可作为 A 的简化实现） |

**执行顺序约束（必须遵守）**：策略 A/B 的实现都排在兜底通道之后。开发顺序：

1. 先完成 WakeUp CSV 导入 + 手动添加（保证 App 功能闭环可用）；
2. 真机/浏览器完成一次真实抓包，确定「我的课表」接口路径、方法、响应结构（Phase 0 遗留 OPEN 项 #2，此为唯一阻塞点）；
3. 按抓包结果实现策略 A；A 覆盖不了的形态用 B 补；
4. 两者都失败时（学校改版期），导入页必须显示明确降级提示并引导 CSV/手动通道——**App 永远不因主通道失效而不可用**。

**隐私与合规硬约束（红线，违反即不合格）**：

- 账号、密码、验证码只存在于 WebView 渲染的登录页里，App 代码禁止读取/存储/上传任何凭据字段。
- `android:allowBackup` 必须配置 `dataExtractionRules`/`fullBackupContent` **排除 WebView 数据目录与 Cookie**（否则 SSO 会话 Cookie 会被 Android 自动备份到用户 Google 云端，属凭据外泄面）。
- Release 构建必须关闭 `WebView.setWebContentsDebuggingEnabled`（仅 debug 构建开启，用于开发期抓包排错）。
- 禁止实现任何验证码自动绕过（OCR/打码）。滑块由用户手动完成，这是 WebView 方案的天然优势而非缺陷。

| DataStore | 0.2 MB | |

## 5. 教务解析器隔离架构（改版只改一处）

### 5.1 设计目标

学校教务系统改版（换接口路径、换 JSON 字段、换前端框架）是本项目**唯一确定会发生**的维护事件。架构必须把它的影响半径压缩到 `parser/xpu` 一个包内，其余代码零改动。

### 5.2 解析器接口（parser/api）

```kotlin
/** 所有解析器的统一入口。I 为原始输入类型。 */
interface PayloadParser<I> {
    /** 解析成功返回课程与节次；失败返回结构化错误，禁止抛裸异常穿透到 UI。 */
    fun parse(input: I): ScheduleParseResult
}

sealed interface ScheduleParseResult {
    data class Success(val schedule: ParsedSchedule) : ScheduleParseResult
    data class Failure(val error: ParseError) : ScheduleParseResult
}

/** 结构化解析错误：改版时的用户提示与日志排查都靠它，禁止统一吞成"解析失败"。 */
sealed interface ParseError {
    data object EmptyPayload : ParseError            // 拦截到了空响应
    data class SchemaMismatch(val detail: String) : ParseError  // 字段结构对不上（学校改版信号）
    data class InvalidData(val detail: String) : ParseError     // 数据本身矛盾（如周次越界）
}
```

`ParsedSchedule` 是纯领域模型（课程 + 节次列表 + 学期信息），不含任何学校系统痕迹——这是"改版只改一处"的类型级保障：**下游永远只认识领域模型，不认识教务 JSON**。

### 5.3 西工程大专属实现（parser/xpu）

```
parser/xpu/
├── XpuEndpoints.kt        唯一的端点配置：登录页 URL、课表接口 URL 特征（正则）、
│                          站点域名常量。学校改路径只改这个文件。
├── XpuJsonParser.kt       策略 A 的 JSON → ParsedSchedule 实现
├── XpuDomParser.kt        策略 B 的 DOM/注入数据 → ParsedSchedule 实现
├── dto/                   @Serializable DTO（与教务 JSON 字段一一对应，@IgnoreUnknownKeys 容忍未知字段）
└── fixtures/              抓包样本 JSON 金样本（测试固定数据），随仓库提交
```

**教学级说明**：为什么 DTO 与领域模型分开放？DTO 的形状由学校接口决定（会变），领域模型的形状由本 App 业务决定（稳定）。二者共存于同一个类，改版时业务代码就会被连带污染——这就是"防腐层"（Anti-Corruption Layer）在小型项目里的落地形态。

### 5.4 导入通道统一入口（importer/api）

```kotlin
interface ScheduleImporter {
    val source: ImportSource                       // WEB / WAKEUP_CSV / MANUAL
    suspend fun import(payload: ImportPayload): ImportResult
}
```

所有通道（WebView 捕获、CSV、手动编辑）最终都汇入 `TimetableRepository.applyImport(ParsedSchedule)` 同一入口入库。**仓库不关心数据从哪来**，这保证了兜底通道与主通道共享全部去重/合并/学期切换逻辑，不会长出两套入库代码。

### 5.5 优雅降级路径（接口未知期的开发顺序）

```
用户点「导入课表」
 ├─ 主通道可用性检测（改版检测）：发起 WebView 会话
 │   ├─ 策略 A 命中特征 URL 且 SchemaMismatch → 已知改版信号
 │   ├─ 策略 A 未命中 + 策略 B 失败 → 显示明确提示：
 │   │    「教务系统疑似改版，一键导入暂不可用。
 │   │     可先用 WakeUp CSV 或手动添加，我们会尽快适配。」
 │   │    （提示文案随版本更新，此处为规则示意而非定稿文案）
 │   └─ 成功 → 解析 → 预览确认页 → 入库
 └─ 兜底通道始终在导入页一级入口可见，不藏在深处
```

配套机制：`import_logs` 表记录每次导入的来源/状态/条数。用户报"导入坏了"时，第一句话问的应该是这张表的内容，而不是让用户复现。

## 7. Room Schema 草案（Room 3.0.3 / androidx.room3）

### 7.1 ER 图

```
terms 1 ──────── n courses 1 ──────── n course_sessions
        （courses.term_id）    （course_sessions.course_id）
time_slots（独立表，作息时间）
import_logs（独立表，导入审计）
```

学期归属链：`terms → courses → course_sessions`，两级级联删除（删学期连带删课程与安排）。**学期过滤的锚点在 `courses.term_id`**（而非 course_sessions），因为"一门课属于哪个学期"是课程级事实，同一门课在不同学期是两条 courses 记录。

课表建模说明：`courses` 是"一门课"（名称、教师、颜色、所属学期），`course_sessions` 是"这门课的一次固定上课安排"（一门课可以周三 1-2 节 + 周五 3-4 节两处安排）。这是课表类产品的标准拆法，直接支持周视图按格渲染与去重合并；学期归属放在 courses 层，使"重复导入覆盖本学期"（Spec AC-13）可通过按 term 清理后重建实现，且不牵连其他学期数据。

### 7.3 关键查询示意（Room 3，Flow 返回）

```kotlin
@Query("""
    SELECT s.*, c.name, c.color_tag FROM course_sessions s
    JOIN courses c ON c.id = s.course_id
    WHERE c.term_id = :termId
      AND s.day_of_week = :dayOfWeek
      AND s.start_week <= :week AND s.end_week >= :week
      AND (s.week_type = 'ALL'
           OR (s.week_type = 'ODD' AND :week % 2 = 1)
           OR (s.week_type = 'EVEN' AND :week % 2 = 0))
""")
fun observeDay(termId: Long, dayOfWeek: Int, week: Int): Flow<List<SessionWithCourse>>
```

`termId` 过滤是必需条件而非可选优化：没有它，两个学期的课程会串台显示（Spec AC-13 的验收点）。对应仓库签名 `observeWeek(termId, week)` 见 §8.1，`termId` 由 ViewModel 层从 `observeActiveTerm()` 注入。

MVP 阶段不建复合索引（`term_id` 单列索引已满足当前数据量），等真机出现查询耗时再优化（避免过早优化）。

### 7.4 迁移策略

- Schema JSON 经 `androidx.room3` Gradle 插件导出并提交仓库（Room 3 强制要求）。
- 本 Schema 为 **v1 初始结构**：`courses.term_id` 等发布前的结构修订直接折叠进 v1，不产生迁移（首个公开版本尚未发布，无存量库需升级）。
- MVP 期（版本 1.x）允许 `fallbackToDestructiveMigration`——本地数据可由重新导入恢复，避免新手维护迁移 SQL；**v2 起禁止破坏性迁移**，必须写 AutoMigration（触发条件写入 ADR-003）。

## 8. 内部模块接口契约

本项目无后端、无 REST API。"接口契约"= 以下 Kotlin 接口签名。**上层只允许通过这些签名调用下层；签名变更等同 API 破坏性变更，必须先改本文档再改代码**（活规格纪律）。

### 8.1 TimetableRepository（domain/repository，由 data/repository 实现）

```kotlin
interface TimetableRepository {
    /** 周视图数据源：给定学期与周次，观察该周全部课程安排。 */
    fun observeWeek(termId: Long, week: Int): Flow<WeekSchedule>

    /** 当前激活学期（无则 null，UI 显示引导页）。 */
    fun observeActiveTerm(): Flow<Term?>

    fun observeTimeSlots(): Flow<List<TimeSlot>>
    suspend fun updateTimeSlot(slot: TimeSlot)

    /** 手动添加/编辑课程（含其全部上课安排，整体替换）。 */
    suspend fun upsertCourse(course: Course, sessions: List<CourseSession>)

    suspend fun deleteCourse(courseId: String)

    /** 所有导入通道的统一入库入口。事务写入并记录 import_logs。 */
    suspend fun applyImport(schedule: ParsedSchedule): ImportSummary

    /** 提醒调度用：下一节课（相对给定时间）。 */
    suspend fun findNextClass(fromEpochMilli: Long): NextClass?
}
```

**契约要点（2026-09-16 与 data 层对齐后确认）**：

1. `observeWeek(termId, week)` 的 `termId` 为**必填形参**，不提供"内部查激活学期"的重载。理由：调用方显式指定学期保留了未来多课表/历史学期查看的灵活性，且让数据流向在调用点可见（隐式查激活学期会把"当前学期是什么"这一业务判断藏进数据层）。**termId 由 ViewModel 层注入**：`combine(observeActiveTerm(), currentWeekSelector())` → 取 `term.id` → 传给 `observeWeek`（见 §9.2）。
2. 若 `observeActiveTerm()` 为 `null`（首次启动、尚未建立学期），UI 显示引导页，**不得**调用 `observeWeek` 传入哨兵值；引导页指向导入流程（导入会建立/确认学期，见 8.2 第 2 条）。
3. `findNextClass` 语义默认限定激活学期；签名保持无参（与 data 层实现一致），不额外传 termId。
4. 配套领域模型 `Course` 字段清单（ViewModel/UI 构造与编辑时以此为准，禁止使用 Entity 充当领域模型）：

```kotlin
data class Course(
    val id: String,             // UUID，导入与手动添加统一
    val termId: Long,           // 学期归属（对应 courses.term_id，见 §7.2）
    val name: String,
    val code: String?,          // 课程编号，可空
    val teacher: String?,       // 可空
    val note: String?,          // 可空
    val colorTag: Int,          // 调色板索引（非 ARGB 直存，换主题不失真）
    val source: ImportSource,   // WEB / WAKEUP_CSV / MANUAL
    val editedAt: Long?,        // 用户最后手动编辑时间；非空 = "导入后被用户改过"（见 §8.2 编辑归属不变量）
    val createdAt: Long,
    val updatedAt: Long,
)
```

5. 编辑路径约束：UI 编辑页**禁止自行拼装** `source`/`editedAt`（例如手工 `course.copy(source = MANUAL)`），必须调用 domain 层纯函数 `Course.markEdited(nowMillis)`（见 §8.2 第 10 条）。这条约束的意义是让"编辑即保护"的语义只有一处实现，未来调整规则不必搜遍 UI 代码。

### 8.2 ScheduleImporter / PayloadParser

见 5.2 与 5.4 的签名。补充约定：

- `ImportPayload` 为 sealed：`WebCapture(val rawJson: String)` / `WebDom(val domJson: String)` / `WakeupCsv(val content: String)`。
- `ImportResult` 为 sealed：`Success(summary)` / `Failure(error: ImportError)` / `Cancelled`。
- `ImportError` 分类必须完整覆盖：`NetworkUnreachable`（校外可达性检测失败）、`NotLoggedIn`（会话失效）、`CaptureMissed`（未拦截到特征响应）、`ParseFailed(ParseError)`、`ValidationFailed(detail)`、`Unknown(detail)`。**禁止实现时新增裸 Exception 通道**——每类错误都对应导入页一条用户可理解的提示与一条 import_logs 记录。

**学期归属 + 写入归属规则（`applyImport` 的前置条件与写入语义，2026-09-16 与 data 层对齐，同日经评审裁决 AC-13）**：

*第一部分：学期归属（数据写到哪个学期）*

1. 目标学期解析优先级：① `ParsedSchedule.term`（解析器从课表页的学年学期筛选值解析得到，**主通道必须尽力产出**，这是"导入即归属正确学期"的第一保障）；② 回退到库内激活学期（`is_active = 1`）。
2. 两者皆无（首次启动、库里没有任何学期、解析器也没解析到学期）→ **必须返回 `ValidationFailed`，不得静默创建学期、不得写空数据**。导入页收到后展示"请先确认学期信息"并进入学期确认步骤。
3. 导入预览页必须显示"即将导入到：<学期名>"，让用户在事务写入前纠正归属——这是"不同学期互不串台"在 UI 侧的对应保障。
4. 提示：手动添加与 WakeUp CSV 通道本身不携带学期信息，因此**必须在存在激活学期时才能使用**（导入页与手动添加页共用同一条前置校验；缺失时先走学期建立引导）。
5. 各通道（WEB / WAKEUP_CSV / MANUAL）都必须走上述同一解析规则，禁止在某个通道内自行决定学期——单一入口 `applyImport` 是学期归属的唯一裁决点。

*第二部分：写入归属（替换范围如何切分）*

6. **替换范围按导入来源切分，各来源互相独立**：`applyImport` 的删除范围是 `(term_id = 目标学期 AND source = 本次导入来源)`，Web 导入只替换 `WEB` 记录、CSV 导入只替换 `WAKEUP_CSV` 记录。禁止跨来源删除。
7. **不变量（P0，永久生效）：`source = MANUAL` 的课程永不被任何导入删除（对应 Spec 验收 AC-20）。** 该不变量与"导入失败绝不破坏已有本地数据"同属数据安全底线；任何未来重构（如整学期重导入、批量编辑）都不得违反。违反即验收不通过。
8. 同源重复导入**不得产生重复累积**：同一来源的记录在该学期内被整体替换，重复导入 N 次的结果与导入 1 次一致（幂等语义）。
9. **疑似重复只提示、不自动合并**：与 MANUAL 课程同名（判定规则由 UI 层实现并保持简单，如名称全等）时，预览页提示"疑似重复 N 门"由用户自行判断；**禁止自动合并或自动删除**——自动改写用户数据会造成难以预期的后果。
10. **编辑归属不变量：用户编辑 ⇒ 失去导入来源身份 ⇒ 获得 MANUAL 保护（2026-09-16 评审裁决，P0，对应 Spec 验收 AC-22）。** 用户手动编辑任一课程后（无论其原 `source` 是什么），该课程 `source` 必须置为 `MANUAL` 并记录 `edited_at`。实现为 domain 层纯函数：

```kotlin
/**
 * 用户编辑标记：返回 source=MANUAL、editedAt=nowMillis 的副本。
 * UI 编辑路径的唯一入口；对本来就是 MANUAL 的课程幂等（只刷新 editedAt/updatedAt）。
 */
fun Course.markEdited(nowMillis: Long): Course = copy(
    source = ImportSource.MANUAL,
    editedAt = nowMillis,
    updatedAt = nowMillis,
)
```

- **为什么必须置 MANUAL**：若编辑后保留原 `source`（如 `WEB`），下次同源导入会把该课程当作同源记录整体替换——用户的改动被**无提示**清除。这是与"按来源替换"机制配套的必要保护；仅在预览页给泛泛提示不足以防住（用户不会预期"我改过的课会消失"）。
- **代价与可接受性**：置 MANUAL 后，下次导入可能产生与导入记录同名的条目（因为该课不再参与同源替换）。该代价是**可见且可自行清理**的——AC-21 已要求预览页提示"疑似重复 N 门"，用户可自行删除，属可逆后果；与"静默丢失用户改动"的不可逆后果不对称，故取此侧。
- **溯源不丢**：`edited_at` 保留"该课程曾来自导入且被用户改过"的信息（否则永久丢失）；同时该计数会体现在 `preservedManualCount`（编辑过的课程自此计入被保护集合）。
- **实现位置**：纯函数放在 `domain/model/Course.kt`，UI 编辑页只调用 `markEdited(now)`，禁止自行 `copy(source = MANUAL)`（见 §8.1 契约要点 5）。

*第三部分：ImportSummary 字段（UI 渲染预览页的依赖）*

```kotlin
/** applyImport 的返回值。UI 预览页与导入结果页依赖这三个计数，缺一不可。 */
data class ImportSummary(
    val termId: Long,
    val termName: String,
    val source: ImportSource,
    val replacedCount: Int,        // 被本次导入替换的"同来源"课程数（覆盖范围提示的数据来源）
    val importedCount: Int,        // 本次实际写入的课程数
    val preservedManualCount: Int, // 该学期内被保留的 MANUAL 课程数（向用户证明手动课程未被删除）
    val suspectedDuplicateCount: Int, // 与 MANUAL 课程疑似重复的课程数（仅提示，不合并）
)
```

约定：

- 预览页（写入前）用 `replacedCount` / `preservedManualCount` 渲染覆盖范围说明，用 `suspectedDuplicateCount` 渲染疑似重复提示；**覆盖范围必须在用户确认前展示**（不做事后告知）。
- 结果页（写入后）用同样三个计数向用户复述实际发生了什么（"已替换 N 门，保留手动课程 M 门"）。
- `preservedManualCount` 必须来自真实查询而非推算——它是"手动课程未被删除"这一不变量的可验证证据，也是导入日志之外第二条可审计线索。
- `import_logs` 建议一并记录 `replacedCount` 与 `preservedManualCount`，便于用户反馈问题时快速定位（字段扩展见 §7.2）。

## 9. 关键数据流明细

### 9.1 导入主通道（策略 A 时序）

```
1. 用户在导入页点「从教务系统导入」
2. WebCaptureScreen 打开内置 WebView（非系统浏览器，保证可拦截）
3. 用户完成登录（滑块/扫码/短信，全部手动，App 零接触）
4. 用户点开「我的课表」页面
5. ScheduleCaptureWebViewClient.shouldInterceptRequest 逐请求比对 XpuEndpoints 特征
6. 命中 → OkHttp 代发请求（GET 场景）→ 响应体分流：
   [副本1] 包装成 WebResourceResponse 返回 WebView（页面正常渲染，用户无感知）
   [副本2] RawPayload 交给 WebImportCoordinator
7. resolve() → XpuJsonParser.parse() → Success(ParsedSchedule)
8. 导入预览页（必须展示：目标学期、覆盖范围＝将被替换的同来源课程数、手动课程不会被删除的说明、疑似重复提示）→ 用户确认 → repository.applyImport()（按来源替换，MANUAL 保留，见 §8.2）
9. Room 事务写入 → Flow 触发 → 周视图/小组件自动刷新 → 提醒全量重排
```

失败注入点与对应行为（教学级完整枚举，防 happy-path 偏差）：

| 注入点 | 表现 | 必须的行为 |
|--------|------|-----------|
| 站点不可达（校园网限制） | WebView 加载超时 | 捕获网络错误，提示「当前网络无法访问教务系统，请在校园网或可访问环境重试」 |
| 登录会话失效 | 拦到的响应是登录页 HTML 而非 JSON | NotLoggedIn，提示重新进入并登录 |
| 未命中特征 URL（改版） | 步骤 5 始终未命中 | 30 秒超时后转策略 B；B 也失败 → CaptureMissed → 降级提示 |
| JSON 结构变化（改版） | parse 返回 SchemaMismatch | 显示「教务系统疑似改版」提示 + import_logs 记录 detail |

### 9.2 周视图显示流

```
TimetableViewModel
  = combine(repository.observeActiveTerm(), currentWeekSource())
  → 取 term.id 作为 termId（term 为 null → 发引导态，不调用 observeWeek）
  → repository.observeWeek(termId, week)
  → WeekSchedule → WeekGrid 渲染
当前周计算：term.startDate 与今天差值 / 7 + 1，用户可在设置页手动校正（preferences.currentWeekOverride）
```

要点：`termId` 由 ViewModel 显式注入（数据层不做隐式激活学期查询，见 §8.1 契约要点 1）；`observeActiveTerm()` 为 null 时进入引导态，指向导入流程（首次使用路径：导入 → 建立/确认学期 → 才有课表）。

### 9.3 提醒流（课前 N 分钟通知）

```
触发重排：applyImport / upsertCourse / deleteCourse / 偏好变更
ReminderScheduler.rescheduleAll():
  1. 从仓库取下一节课（结合 time_slots 换算绝对时间）
  2. AlarmManager.setExactAndAllowWhileIdle 设定该节课前 N 分钟
  3. WorkManager 每日周期任务校准（跨天/系统重启后重排）
ClassAlarmReceiver → NotificationHelper 发通知（渠道：课前提醒）
权限：Android 13+ POST_NOTIFICATIONS 运行时申请；
     Android 12+ 精确闹钟：检查 canScheduleExactAlarms()，未授权降级 setWindow 并在设置页说明
```

### 9.4 小组件流

```
Glance NextClassWidget：展示下一节课（课名/教室/倒计时节次）
数据：订阅 repository（Glance 侧通过定期更新 + 数据变更触发刷新）
约束：小组件是"只读视图"，不承担编辑功能
```

**已知坑内嵌（生成式代码防线）**

## 12. 端到端验证步骤（架构交付的完成定义）

以下步骤全部通过，本架构才算交付完成：

1. **构建门**：`./gradlew assembleDebug assembleRelease` 通过，无版本解析错误（【核对】项在此步闭环）。
2. **图标门**：全局搜索 `material-icons`、`Icons.Filled`、`R.drawable.lucide`（AppIcons.kt 除外）、界面代码中的 emoji，命中数必须为 0。
3. **分层门**：静态检查 ui/ 目录无 `androidx.room3`、`androidx.datastore`、`android.webkit` import；data/ 目录无 `androidx.compose` import。
4. **文件门**：`find app/src/main/java -name '*.kt' | xargs wc -l` 无超 300 行文件；TimetableApp.kt / MainActivity.kt 不超 100 行。
5. **功能闭环（模拟数据）**：在 parser/xpu/fixtures 金样本上跑 `XpuJsonParser` 单测通过 → 用测试按钮将 fixture 注入 applyImport → 周视图正确渲染含单双周课程 → 编辑一门课 → 周视图即时刷新。
6. **错误流验证**：将 fixture 换成截断 JSON，单测必须返回 `SchemaMismatch` 而非抛异常；导入页收到结构化错误并显示对应提示。
7. **隐私门**：manifest 审查 allowBackup 排除规则；release 包反查 `setWebContentsDebuggingEnabled` 调用点为 BuildConfig.DEBUG 条件内。
8. **真机主流程**：真机安装 debug 包 → WebView 完成一次真实登录 → 打开我的课表 → 拦截成功入库 → 课前提醒按 time_slots 实际时间触发一次 → 小组件显示下一节课。

其中第 8 步依赖抓包完成后的主通道实现；在此之前以第 5 步（fixture 注入）作为先行的架构验证等价物。
